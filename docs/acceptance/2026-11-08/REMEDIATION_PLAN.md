## 一、F1：将已知源缺口传播到业务与统计窗口

### 1. 根因与修改位置

当前 Step 03 保存了 gap lineage，但 Step 04 主要根据保留快照求值，没有使用这些缺口约束窗口。隔离记录已不在普通数值表中，因此仅检查数值表是否有 NA 无法识别源缺口。

主要修改位置：

- `research/execution.py`：解析当前冻结源的 gap refs，按实际读取范围构造算子上下文。
- `research/business_windows.py`：四类业务窗口均执行与自身依赖相符的缺口判断。
- `research/statistical_windows.py`：统计采样不得通过 as-of 填充跨越相关已知缺口；trailing 窗口传播上游失效与源缺口。
- `research/onboarding_adapter.py`：复用现有 gap reader；需要优化时增加有界过滤或索引，保留冻结文件及 hash。
- 相应 audit schema、结果校验器及测试。

上述路径均相对于 `quantsage_discovery/`。

### 2. 解决方案

**A. 显式传递缺口上下文。**

执行层根据 DataSource 的精确版本和 gap manifest/hash，加载当前合约、交易日、session 和授权历史范围内的相关事件。上下文至少包含：

| 字段 | 用途 |
|---|---|
| gap manifest ref/hash、policy version | 固定缺口来源与规则，参与计算身份 |
| event ID、类型、确定性、点/区间边界 | 判断影响时间及是否需要保守失效 |
| affected fields | 与 primitive/业务输入角色的字段依赖匹配 |
| evidence ref、源记录 ID | 从窗口审计追溯到隔离行或源证据 |

不能只传一个全局“存在缺口”标志，也不能只查询输出范围而漏掉 lookback/统计历史内的缺口。`session_id` 为空但能按合约、日期、时间定位到本 session 的相关事件，需要按冻结规则处理，不能因等值过滤而遗漏。

**B. 按字段依赖确定影响。**

- 盘口字段的隔离事件影响依赖该字段的 OBI、WOBI 等窗口。
- 累计量连续性无法证明时，相关 flow 窗口失效；不得假定隔离期间无 reset。
- 明确无关的字段异常不应使无关特征失效。
- `VOLUME_INCREMENT_UNVERIFIED`、对账不一致等既有警告只传播警告，不单独变成缺口。
- 普通无更新不自动等于丢包；只有明确配置并冻结的 age/间隔上限才产生相应失效。
- F06 单快照不可完成仍按原公式的有效快照均值处理，不能把它直接升级成源行情缺口。

**C. 冻结时间边界。**

窗口保持 `(t-L,t]`。对点缺口 `g`，若 `t-L < g <= t`，且影响当前依赖，输出 NA。点缺口恰在左边界时不属于窗口内部，但端点型公式仍须另行验证命中端点及累计量连续性，不能仅凭开区间判定有效。

区间缺口遵守事件记录的 boundary 语义；不能把所有事件强行转换为同一种开闭区间。未知起止范围按冻结策略保守处理，保留 unknown，不编造缺失记录或连续性。恢复必须同时满足无相关缺口、完整历史及算子自身的有效性条件。

**D. 在 Step 05 保留失效链。**

统计窗口中只要所需样本遇到相关 gap、NA 或 stale，该完整 trailing 值就为 NA，不 dropna 拼接，也不通过重复前值绕过已知缺口。primitive-only 统计同样需要检查源缺口，不能只修复 business-input 分支。

上游 L 窗口受缺口影响时，统计值恢复还要等待完整 W 的有效采样历史。具体恢复时刻按冻结 sampling 网格计算，不简单用“缺口时间 + L + W”替代实际窗口判断。

**E. 保存可验证审计。**

建议新增明确原因 `KNOWN_SOURCE_GAP`；它是本次待新增错误码，实施时同步登记、校验和计数。若已有多个失效原因，冻结主原因优先级，并保留 gap 证据，不能让主原因覆盖丢失血缘。

每个受影响窗口应能查到主原因、匹配事件 ID、gap manifest ref/hash，以及通向源记录的引用。事件较多时使用独立审计表和稳定引用，避免把大量证据重复嵌入每行。

### 3. F1 验收标准

| 测试 ID | 场景 | 必须满足的断言 |
|---|---|---|
| F1-01 | OBI 窗口内部存在已知盘口隔离点 | value 为 NA，原因明确，gap event ID 可追溯 |
| F1-02 | 点缺口恰在 t、恰在 t-L、刚在窗口外 | 分别验证右闭左开及端点依赖规则，禁止模糊浮点边界判断 |
| F1-03 | 区间缺口、未知连续性、session 为空的可定位事件 | 按冻结边界/确定性策略处理，不能静默跳过 |
| F1-04 | 无关字段异常、无更新、仅对账警告、F06 不可完成快照 | 不被无条件标成源缺口；保留原公式和警告规则 |
| F1-05 | 缺口后逐步追加足够历史 | 完整 L 满足前保持 NA，满足后在合法观察时刻恢复 |
| F1-06 | business-input 和 primitive-only 的 Step 05 | 相关 gap/NA/stale 使 trailing 值 NA；完整有效 W 后恢复 |
| F1-07 | 其他合约/日期/session 的 gap | 不影响当前独立窗口；午休/隔夜不拼接 |
| F1-08 | 相同时间前缀，追加未来行情及未来 gap | 已结束窗口的值与有效性不变 |
| F1-09 | 序列化执行与消费 | Result/audit schema、计数、原因与 lineage 一致；不能只在内存函数中正确 |

**强制真实反例：** 使用冻结源 `cffex_treasury_l2_full79@2`，`TS2606 / 2026-06-12` 上午 session，检查 `01:34:11.800 UTC` 的 1m OBI。它跨过 `01:34:00.800 UTC` 的 `INVALID_L1_BOOK` 隔离事件，修复后必须为 NA，并关联 event ID：

```text
767c1fecbf12259a834995654f3bb6753b04e8d5806f261a40824530a4c01592
```

验收必须明确读到该时刻、该事件及相应非空输入。零行、删除该时刻、全部任务 BLOCKED 或所有输出一律 NA，均不构成通过；另以有充分历史且无 gap 的对照验证正常数值和恢复。

## 二、F2：分离输出范围与历史可用边界

### 1. 根因与修改位置

`business_windows.py` 的 `_rolling_mean`、`_flow_windows`、`_volume_depth_window`、`_mid_move_window` 使用 `partition.start` 判断历史是否充分。该字段表示输出范围起点，而 planner 已通过 `read_scope` 展开所需过去历史，两者不能等同。

### 2. 解决方案

**A. 统一窗口上下文。** 四类算子共享一份明确的执行上下文，可采用必传 keyword-only 参数，包含真实 session 起止、实际授权读取范围、历史 shortfall、缺口信息。上下文必须来自冻结计划和源 session 规则，不能由算子猜测。

| 时间概念 | 职责 |
|---|---|
| output scope | 决定哪些时刻发布结果 |
| read scope | 决定允许并实际读取哪些依赖数据 |
| session bounds | 限制连续历史，禁止跨午休、隔夜和真实合约 |
| required history / shortfall | 描述目标窗口需要的历史及明确缺失 |
| input availability / split permissions | 限制当时及当前研究权限可用的数据 |

禁止默认 `history_start=output_start`；也不能仅取“第一条有效快照时间”作为历史边界，因为无更新、无效值和缺口具有不同语义。

**B. 修正充分性判断。**

1. 根据 t、L、端点 age 等冻结规则确定 required history。
2. 用真实 session 和授权读取范围检查能否覆盖所需历史。
3. 根据快照掩码、端点匹配、reset、缺口等规则计算数值或 NA。
4. 最后仅发布 output scope 内结果；历史依赖仍可保留其自身 lineage，但不混入本特征请求的输出范围。

Step 04 应通过管理执行链独立运行；Step 05 只展开所选业务/primitive 依赖，不需要预先人为执行更宽范围来规避问题。缺失 session/history 上下文时给出明确校验失败，不能静默退回旧行为。

**C. 保持原公式。** 仍使用快照算术均值、既定端点 backward as-of、显式 max_endpoint_age、reset 和零分母规则。仅修正历史判定，不把快照均值改成时间加权或重采样均值。

### 3. F2 验收标准

| 测试 ID | 场景 | 必须满足的断言 |
|---|---|---|
| F2-01 | 相同输入、授权历史和 session，只改变输出起点 | 共同时间点的值、有效性和失效原因一致 |
| F2-02 | 四类窗口分别测试 | F01–F06 均值、F09/F12 flow、F10 volume/depth、F11 mid-move 都满足 F2-01 |
| F2-03 | 从 session 中途启动真实 Run | plan 展开历史，serialized Result 与宽范围 Run 的共同时间点一致 |
| F2-04 | primitive → business → statistical 依赖链 | 中途开始统计请求不会导致其 business 前 L 区间凭空 NA；统计网格仍锚定真实 session |
| F2-05 | session 开头不足 L、午休/隔夜、缺授权历史 | 保持 NA 或明确 BLOCKED；不能扩大权限补历史 |
| F2-06 | t-L 恰有观察、超端点 age、reset、相关 gap | 原有端点、reset 和 F1 规则仍生效 |
| F2-07 | 冷启动、缓存命中、resume | 同一冻结定义与合法范围的数值一致；改变输出范围不修改历史结果 |

**强制手算反例：** 同 session 在秒数 `[0,20,40,60,80]` 的值为 `[0.8,0,0.4,0.6,-0.2]`，L=1m，提供同样的完整授权历史。

| 时刻 | 宽输出范围 | 输出从 60s 开始 |
|---|---:|---:|
| 60s | 1/3 | 1/3 |
| 80s | 4/15 | 4/15 |

有限数值比较使用 `atol=1e-12, rtol=1e-12`；NA、原因、时间及 ID 精确比较。不要求不同范围或运行的 artifact/result ID 相同，但它们都必须能追到正确历史输入。

## 三、F3：修正目录名称并处理历史兼容

### 1. 根因与修改位置

`business_windows.py::_entry` 使用 `key[0]` 拼接 space 前缀，得到 `s0` 而非原规格的 `d0`。

### 2. 解决方案

1. 按参数语义显式拼接名称：space 直接使用规范值 `d0/d1/d2/d3/d5`，size 使用 `q25/q50/q100`，lookback 使用规定的 h 后缀。先校验取值，再生成名称。
2. 不从参数键名首字母推断业务记号。固定参数后缀顺序，组合名称与输入字典顺序无关。
3. 逐项对照原规格目录，保留 432 项数量、唯一性、family counts、48 项 pending 状态及合法组合约束。
4. 检索错误名称是否用于导出、CLI、FeatureSet、结果引用或用户配置。历史 Feature/FeatureSet/Result 不原地改名重写；保存旧名称及所属版本以便审计。若已有外部消费，提供显式且无歧义的旧名到规范名映射，标注兼容范围；新目录只输出规范名。
5. 名称若仅为展示元数据，修正本身不应无故使无关数值失效；若参与定义身份或配置解析，则发布相应新版本并验证引用行为。不能为了保留缓存而保留错误命名。

### 3. F3 验收标准

| 测试 ID | 场景 | 必须满足的断言 |
|---|---|---|
| F3-01 | 首个 F02 条目 | 名称精确为 `obi__d0__h1s` |
| F3-02 | 各 space、size、lookback 组合 | 名称符合原规格；不存在错误 `__s0` 至 `__s5` 或重复 d/q 前缀 |
| F3-03 | 完整目录 | 与独立冻结的原规格名称集合逐项相等，不仅比较数量 |
| F3-04 | 数量、状态与合法域 | 总数 432、唯一；family counts 为 `8,40,40,120,120,24,24,24,8,8,8,8`；pending 仍为 48；不生成非法组合 |
| F3-05 | 参数键顺序变化 | 生成相同规范名 |
| F3-06 | 实际存在的目录消费入口与序列化输出 | 均使用规范名；不得只修复内存目录而遗漏导出或解析 |
| F3-07 | 历史对象和旧名兼容 | 历史对象可读且未被覆盖；如提供映射，不能把不同定义合并成一个名称 |

名称预期集合应来自原规格的独立 fixture 或人工审定清单，不允许通过调用待测名称生成函数创建预期值。

## 四、版本、缓存及结果发布

F1/F2 改变数值或有效性，必须发布新的实现身份。已有错误结果保留为历史，不原地覆盖，也不删除原研究库规避问题。

- 使用现有 catalog/provider/definition 版本机制发布新版本，刷新受影响的冻结 FeatureSet；不能把新版逻辑挂在旧 implementation_version 下。
- 计算身份覆盖实际相关的实现版本、输入结果身份、gap policy/manifest hash、source refs、历史权限/边界等。若现有指纹已覆盖某字段，复用该机制，不重复发明身份规则。
- 已冻结旧定义只能按其声明的语义执行或被明确标记不支持，不能静默换成新算法。若现有执行器无法路由旧实现，应明确拒绝旧定义的新执行，同时允许审计读取历史结果。
- F1/F2 新结果不得命中旧业务窗口数值；依赖该业务结果的统计计算必须重新判定身份。primitive-only 的 gap 修复也需更新相应实现身份。
- 未改变定义、实现和所需证据的 primitive 仍可复用；新版本相同配置重复执行应稳定命中合法缓存。
- artifact schema 变化时同步版本和校验器。NA 产物可成功发布，但必须与缺文件、执行失败、NO_WORK 区分。

**缓存验收：** 在隔离库预置旧实现结果后执行新 FeatureSet，确认新业务计算不复用旧错误产物，统计下游不复用依赖旧结果的缓存；再次运行新版时正常复用新版结果。改变相关 gap hash 或历史权限后也不能误命中原指纹。保留 producer、attempt、结果及 lineage 证据。
